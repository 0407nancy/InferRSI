# InferRSI loop

这是一个通用编排 skill，不复制执行逻辑，不为场景创建子 skill。模型只在本机调用，远端执行实验。

## 定位与配置

从用户指定目录或当前工作区定位项目，读取 README、适用 AGENTS.md。首次使用从 `config/launch.template.json` 和 `config/task.template.json` 创建用户自己的启动与任务基础配置；按 README 字段说明核实本机入口、目标容器、源码、权重、推理环境和资料路径。所有占位符必须填完，可选来源无内容则删除。不要默认用户已有运行 JSON，不把 `config/examples/h3-93.*` 个人部署当成通用默认。用户可用 prompt 说明需求，也可自行编辑模板。

用户只需说明目标。配置优先级：本次明确要求 > 用户指定配置 > 经核实并展示的模板默认值。已有运行继续使用冻结配置，覆盖参数应建立新运行。不要把“最近运行”默认为新的默认配置。

启动前简要展示项目/基线、profile 策略、卡号、测试层级、预热/测量次数、数值与收益规则、轮数/时间预算、恢复预算、记录目标及配置来源。能从配置确定的内容不重复询问；缺少影响有效性或授权的参数再确认。轮数、时间和恢复预算相互独立，不在 skill 写死。不要承诺脚本不支持的能力。

## 组合已有能力

阅读项目 README 和相关脚本参数，复用 `scripts/prepare_task.py`、`local_driver.py`、`run_h3.py`、`supervise_h3.py` 及已有协议。新用户先填模板再 prepare；`make_h3_config.py` 是原 H3 部署兼容助手，不能用它要求新用户拥有旧请求/捕获。局部骨架未准备时应生成真实模块 adapter；采集或 short 消融缺少适配时先补齐，不假装模板已经包含所有工作负载。

- 探索：`task=explore`，通过真实实验反馈继续提出候选。
- profiling：按需求选择 reuse、collect、adaptive；采集命令和次数先冻结。P800 使用 torch profiler 与 xprofiler 串行采集、联合分析；计时收益使用关闭 profiler 的对照。
- 固定消融：`task=ablate`，将明确的补丁/开关及依赖映射为实验矩阵；不自动搜索新优化。leave-one-out、单项组合或其他矩阵由需求和配置决定。
- 查询/记录：只读已有运行，不启动模型探索或实验。
- 新场景：先组合已有配置和能力；缺少测量能力时最小扩展 adapter，不能假装已有支持或复制一套 loop。

## 历史与实验约束

读取指定 profiling、实验文档和运行目录，保留出处/版本。区分已成功、已失败、进行中、待验证；优先新方向，不重复实现成功方案或提交在途实验。重试失败方案必须记录环境、实现或输入的实质变化及依据；基础设施失败不代表优化无效。每轮上下文包含历史摘要及与已有方案的区别。

在 `knowledge_sources` 声明手动文档、loop 文档、当前及旧实验目录和参考资料，不能只收入成功项或飞书列举项。新 run 由本机读取文档/嵌入表格，远端收集原始文本并冻结；缺少必需来源不能当作空历史。检查 `frozen/knowledge/coverage.json`，报告超限、缺失或未读资源；使用完整 `catalog.json` 及正文检索相关旧尝试，InferRSI 的前 20 个摘要不是全部知识。旧版本收益、旧捕获、新版回放旧输入须明确区分。恢复既有 run 不刷新冻结知识；扩大来源创建新配置。

当前 H3 工作流：全仓库可编辑；探索仅局部单测和模块数值验证，消融仅 short E2E。有参数模块使用真实模型权重，可固定输入，无参数模块记录输入来源；禁止随机造权重。沿用冻结数值规则，无适用规则的差异留待确认，不自行放宽。局部达标仅登记候选，不宣称 E2E 收益。卡号、测量次数和门槛从配置读取；不得终止其他任务。

## 独立执行与记录

将原始需求、最终配置及来源、预算、证据位置、历史摘要和记录目标保存到运行目录，不包含凭据。恢复不能依赖当前聊天。检查本机模型、个人 SSH、飞书访问及后台恢复所需权限；SSH 遵循用户连接指南，飞书操作使用本机可用的 lark-doc skill。

授权后台执行时使用 `supervise_h3.py --task-file <absolute-task-file> --recoveries <budget> -- --launch-config <absolute-launch.json> <run_h3参数>`，复用既有 driver 和 reporter。先检查同一运行是否在途，启动后检查真实 PID、状态及日志。当前恢复是有限恢复，受本机 sandbox/认证约束，不保证无人值守解决所有故障；不绕过权限、不修改冻结条件、不覆盖失败证据。同步失败只补传。耗尽预算保留 needs_attention，不自动开新探索。

按授权文档格式记录思路、改动、条件、原始指标、收益、质量结果、结论和证据位置；负收益和未测量也保留。缺少同步回执不声称已记录。项目要求实验记录在飞书时不另建 Markdown 实验报告；README 和 skill 属于项目文档。

## 明确连接入口与预检

读取用户指定的 `--launch-config`（首次由 `config/launch.template.json` 填写）：其中 `ssh_guide/ssh/host/expected_user/expected_hostname` 明确 SSH 入口，`lark/lark_skill/document` 明确飞书入口。它同时配置预检、driver、reporter 和恢复 CLI，不能只改检查目标。入口缺失时先查适用工作区说明、用户指定指南和 PATH，再询问必要缺项；不遍历凭据文件。旧 `config/local-access.json` 及个人 H3 示例仅供对应部署兼容。

读取指南后执行 `scripts/preflight_access.py --config <my-launch.json>`。supervisor 的 worker 也会在实验前预检；失败保存 needs_attention，不调用模型反复重试权限问题。普通终端与沙箱结果不同则检查权限；均失败再检查网络或认证。按工具能力申请必要权限，不自动重置认证或扩大权限。

检查报告的 ready 仅覆盖当前进程的只读访问。恢复 CLI 的网络和凭据权限必须在同样 `--approve-for-me` 环境单独实际执行预检，不能凭外层成功认定通过；未验证时明确报告。飞书写权限未在只读预检中验证，不声称已验证。启动时传入同一 `--launch-config`，并核对任务配置的模型和记录目标一致。

准备新的 H3 运行时读取项目 references/h3/catalog.json 和 guide.txt，并设置 reference_directory 为远端对应目录；复用该手动修复/融合参考包，按需检查版本适用性。只读已冻结运行时不修改配置。参考包的 checkpoint 头信息不是权重内容验证，安装源码不等于纯净上游，旧合成输入不能满足真实权重测试。

H3 资料使用先读 current-rounds.json。严格区分当前源码证据、源码推导布局、当前实测布局和旧捕获；新环境回放旧捕获不自动成为当前真实输入。检查优化分支是否在目标工作负载命中。新运行冻结前验证当前参考源码哈希，不改旧运行。

资料缺口应通过 local_recovery 的 missing_evidence 返回给 driver，在白名单内补齐后继续同一候选；不要直接把缺资料算作有效实验。修复必须保留旧协议固定输入的原始字节和哈希，不能重新造输入绕过缺失。新协议先做迁移后的 baseline 预检，失败由测试生成器根据保留日志修正。冻结后协议故障使用新版本/新评测，禁止覆盖旧证据或降低数值门槛。数值失败和无收益正常保留。展示候选数与 effective_experiments，不用 completed_rounds 冒充实测次数。独立回放验证按 prepare_replay.py 新建配置，在启动后外层只观察，不修补内部任务。

## 实验记录格式

复用现有 reporter，不另建记录 skill。每个新 run 在目标飞书文档新建并列 h2 小节；同一 run 重复同步只更新其原小节，不挂在上一个实验标题下。标题注明时间和 run ID，正文先解释优化瓶颈和改动，再用一句“尝试原因”说明为何预计能减少开销，随后简述实际结果，用简洁表格列出优化项、具体改动、基线/候选耗时、耗时下降、数值验证和结论。注明 Asia/Shanghai 时间及含具体 run ID 的 results.json、补丁、评测文件完整路径。缺测量写“未测量＋原因”，不把运行错误当成优化失败；区分候选数、有效实验数、修复次数，局部收益不外推 E2E。历史记录只整理表达，不改实验原始证据。用户要求独立验收时，运行期间外层只读观察，代码、skill、README 及 reporter 变更等运行结束后再同步。

尝试原因复用 Planner 既有 rationale 字段：每项用简洁中文说明瓶颈依据和预期作用，假设不写成已验证事实，不增加模型调用。reporter 默认输出“尝试原因”；旧记录缺 rationale 时沿用 hypothesis，均缺失时明确待补充。同步前读取本 run 小节，优先保留已手工补充或修改的原因，并保存到运行目录 report-notes.json；重新收集 results.json 和重复同步不得丢失该原因。

## 参数化局部测试

局部测试复用同一脚本，以固定输入 JSON 描述有界测试矩阵；逐项注明源码/模型元数据出处、确定的约束与自主选择的测试值、shape/dtype/stride、分支条件及输入生成规则。覆盖适用分支和多个合理尺寸，边界用例用于数值检查，不单独充当性能指标。有参数模块加载真实权重；无参数模块无需权重。必须调用实际修改的生产代码和后端，不能用重写或 mock 代替。

缺少当前 request 的精确长度时，允许从当前源码约束构造固定输入；标注“固定输入局部验证，真实负载代表性待确认”。冻结每项输入、计时范围、每用例次数和汇总方式，保留逐用例数值/耗时；不挑最快用例，不把元数据创建收益外推为 attention 或整模型收益。更换 request 时复用脚本，新增尺寸补用例；dtype/并行/批处理/分支变化重新检查适用性。测试修复不得变更已冻结输入或门槛；探索阶段不运行 short/official request。

资料回补按请求批次计数，当前默认6次；text 支持允许目录内不超过2 MiB的 UTF-8普通文件（含 .log），超限明确拒绝，尚不支持大日志摘录。读取失败必须区分文件类型、大小、路径和缺失；条件不变时不得原样重试。同批合并已知相关文件，不通过提高次数掩盖读取器故障。
